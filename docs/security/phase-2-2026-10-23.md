# SOCIA security hardening, phase 2 (2026-10-23)

Branch `security-hardening-2`, built on `security-hardening` (PR #74). It continues the 2026-10-22 audit (`audit-2026-10-22.md`); that audit is not repeated here.

Status labels:

- **FIXED AND TESTED:** fixed, and an automated test fails if the fix is undone.
- **FIXED BUT NOT INTEGRATION-TESTED:** fixed and unit-tested, but not run against the real platform, a live account or the production database.
- **REQUIRES MANUAL ACTION:** needs Noah (SQL, dashboards, a live account).
- **NOT FIXED:** left as is, with the reason.

SOCIA is not bulletproof. This pass closes the four open high and medium risks from phase 1 and most of the low ones. What is left is listed in section 9.

## 1. Database: migration review and authorization tests

**How it is tested.** `supabase/tests/` builds a real Postgres database (PGlite, Postgres 18 in process) with the parts of Supabase the policies depend on: the `anon`, `authenticated` and `service_role` roles, Supabase's default grants, `auth.uid()` read from the request's JWT claims, and storage with RLS. Every migration is then applied in the order production ran them. Each test request runs the way PostgREST runs one: in a transaction, with `set local role` and the JWT claims set. So a query refused here is refused through Supabase REST.

The fixtures (`seed.ts`) are two customers (A and B), an agency owner (O) with two Brand Workspaces, an Admin and a Member of one of them, and a new person with no workspace. They are inserted **before** `security-hardening.sql` runs, so the migration is tested on existing data. Then the migration is applied a second time to prove it can be re-run. Nothing touches the production database.

`supabase/tests/authorization.test.ts`, 31 tests:

- The migration keeps every row, removes the Page tokens already stored in a pending Facebook list (and keeps the names), and leaves RLS on for every table.
- Signed out (anon key): no row in any table, no stored file, no writes.
- Customer B against customer A, **for every table that has `user_id` or `owner_id`**: B can't see, change or delete any of A's rows. B can't create rows in A's name, can't attach a destination to A's post (so can't publish A's content), can't put rows into A's workspace, and can't list, overwrite or delete A's files. Control: B's own data still works.
- Platform tokens: no browser session can read or write any token table, not even its own rows. The server role still can, so refresh and publishing keep working.
- Workspaces and plans: a browser session creates only its first workspace. Nobody can give themselves a plan, a trial, plan overrides, or change a pause flag.
- Agency roles: an Admin's or Member's own session sees none of the owner's data (the server acts for them by role). A Member sees only their own workspace, not the owner's other brand, and can't read or create invites. An Admin sees, creates and cancels only Member invites. Only the owner changes roles. Nobody can swap who a member is, and nobody can add themselves to a workspace.
- Functions: the anon key can run only the two policy helpers. A signed-in session can run only five functions, each of which reads `auth.uid()` itself and takes no user id from the caller. No guard trigger runs as `security definer`.

**What the tests found** (all FIXED AND TESTED):

| | Problem | Fix |
|---|---|---|
| **D1 (high)** | The three guard triggers from phase 1 (`socia_guard_workspace_insert`, `socia_guard_connection_write`, `socia_guard_workspace_fk`) were `security definer`. Inside them `current_user` is the owner (`postgres`), so `socia_is_privileged()` was always true and **they let every browser write through**. Extra workspaces past the plan limit, rows in someone else's workspace, and connection rows written from the browser were all still possible. | Now `security invoker` (`security-hardening.sql` sections 3, 4 and 9). A test fails if any guard is a definer again. |
| **D2 (medium)** | Admins could read every invite token in the workspace, including the owner's Admin links, and could insert an Admin invite straight through REST, skipping the owner-only rule the app enforces. They could also turn a Member link into an Admin link. | Section 12: separate read, create and cancel policies. Admins handle Member invites only. After creation an invite can only be cancelled (`revoked_at` is the only column a session may update). |
| D3 (low) | `socia_consume_usage` was callable with the anon key. It refuses without a session, but it had no reason to be callable. | Revoked from anon (section 8). |
| D4 (low) | `schema.sql` failed on an empty database (two copies of the same policies). | The second copy is guarded. `schema.sql` is marked run-once, because re-running it would restore superseded, weaker policies. |

**Migration review notes.** `security-hardening.sql` can be re-run safely: the test applies it twice. It deletes no data; section 7 only removes `access_token` keys inside `pending_pages` JSON. **Deployment order matters** because of section 11 (below): deploy the code first, then run the SQL.

## 2. YouTube tokens out of the browser (was H10)

**FIXED AND TESTED (unit); FIXED BUT NOT INTEGRATION-TESTED against YouTube.**

- **Investigation.** Google's resumable upload guide for YouTube sends `Authorization: Bearer` on every chunk and every status query (steps 3 and 4), and never says the session URI works without it. Sending the browser only the session URI therefore isn't documented to work, so SOCIA's server relays the chunks instead.
- **How it works now.** The server opens the session as before. It seals the session URI into an AES-256-GCM handle (key derived from the service-role key) bound to the destination and the owner, valid 24 hours. The browser gets only that handle. Each 4 MiB chunk (a 256 KiB multiple, under Vercel's 4.5 MB request limit) goes to `PUT /api/posts/:id/destinations/:did/youtube-upload`. That route checks the signed-in person, the publish role, that the post and destination belong to the active workspace's owner and are uploading, that the chunk is aligned and the right size, and that the handle was made for this destination. It then forwards the chunk to YouTube with a fresh token. The relay only ever contacts `https://www.googleapis.com/upload/youtube/v3/videos?...upload_id=`.
- **Kept:** resumable uploads, progress (from YouTube's own byte count), retries with backoff and a status query, and the existing confirm-and-poll publishing flow.
- **Removed:** `https://www.googleapis.com` from the browser's CSP `connect-src`.
- Files: `lib/publishing/youtubeRelay.ts`, `app/api/posts/[id]/destinations/[did]/youtube-upload/route.ts`, `lib/publishing/youtubeUpload.ts`, `lib/publishing/adapters/youtube.ts`, `lib/publishing/runner.ts`, `lib/publishing/adapter.ts`, `components/composer/*`.
- Tests: `youtubeRelay.test.ts` (handle binding, tampering, expiry, host allowlist, range rules, YouTube answer mapping, token only ever sent to YouTube). `youtubeUpload.test.ts` (the browser sends no `Authorization` header, talks only to SOCIA, and resumes after a drop). `adapters.test.ts` (what publish hands the browser contains neither the token nor the upload id).
- **Trade-offs:** every video byte now passes through Vercel twice (in and out), which counts toward the Hobby plan's data transfer. Uploads are about as fast, but each 4 MiB chunk is one function call.

## 3. Platform tokens are server-only

**FIXED AND TESTED.** `security-hardening.sql` section 11 revokes every privilege on `instagram_connections`, `facebook_connections`, `youtube_connections`, `tiktok_connections` and `facebook_pending_tokens` from `anon` and `authenticated`. SOCIA's server reaches them through the service role. `lib/supabase/server.ts` wraps the per-request client (`lib/supabase/privateTables.ts`) so that `.from(<token table>)` uses the service role and everything else keeps the person's session and RLS.

- Every token-table query was audited. Each request-path query filters by the owner; only the daily snapshot jobs and Meta's signed deletion callback read every account, on purpose. `lib/supabase/privateTables.test.ts` scans the code and fails if a new query has no owner filter, or if browser code touches these tables.
- No policy, view or invoker function that a browser session runs reads these tables. Two `security definer` functions do, and the revoke doesn't affect them.
- The database test proves a signed-in session can't read `select *` or `access_token`, can't insert, update or delete, and that the server role can.
- OAuth refresh and publishing keep working: they run on the server, which now reaches these tables through the service role.

## 4. Workspace isolation

**FIXED AND TESTED.** Guests (Admins and Members) run with the service role, so only server code keeps one brand of an owner away from another. Fixed:

- Studio clip and build lookups and writes: load, play, edit, regenerate, mark rendered, complete, delete (`lib/studioClips/server.ts` and the `app/api/studio` routes).
- Audio measurement (`lib/audio/server.ts`).
- The Instagram collaborator check, which used any of the owner's accounts and now needs the account to be in the active workspace (`lib/publishing/collaborators.ts`).

Test: `lib/studioClips/workspaceScope.test.ts` runs each lookup against an in-memory table holding rows of two workspaces, asking from one workspace for the other's ids.

## 5. CSP and frontend

- **Unsafe HTML.** The only `dangerouslySetInnerHTML` is `ThemeScript`, a fixed string with no input. There is no `eval`, `new Function`, `innerHTML` or `document.write`, and no third-party scripts.
- **Server code in the browser.** FIXED AND TESTED: `lib/clientBoundary.test.ts` walks the import graph of every `"use client"` file and fails if it reaches code that reads a server secret, creates the service client, or uses `node:` or `next/headers`. One allowed exception is documented in the test.
- **Paid analytics in the page payload.** FIXED AND TESTED for previous-period comparisons: when the plan locks them, `lib/analyticsGate.ts` removes every comparison value on the server for Instagram, Facebook and YouTube. Before, the browser received them and only hid them. Posting-time data: see section 9.
- **CSP violations.** The full policy stays report-only, and the browser now sends violations to `/api/csp-report`. Each one is logged as `[csp] <directive> blocked=<origin> page=<path>`, never with a query string. Verified against a production build: a deliberate violation produced one log line without its `?token=`, and the public pages produced none. A static review of signed-in pages found nothing the policy would block: no iframes, workers only from `blob:`, and Studio fonts from `fonts.gstatic.com`, which is allowed. **Signed-in pages could not be checked in a browser** (I can't sign in), so enforcing waits for real reports (section 8).
- Even when enforced, `script-src` keeps `'unsafe-inline'`: Next's inline bootstrap scripts need it unless every page moves to per-request nonces, which makes every page dynamic. That is a separate decision.

## 9. Remaining risks

- **Posting-time data is still in the page payload** when "Know when to post" is locked: the same data feeds insights every plan sees. Fixing it means computing those insights on the server first.
- Comparison numbers written into server-generated insight text (for example "up 14% vs. the previous period") are not removed by the stripper.
- **The CSP isn't enforced yet**, and when it is, `script-src` still allows inline scripts.
- **The YouTube relay hasn't uploaded a real video yet** (section 8, step 4).
- Guest access to the owner's data still depends on server code passing the workspace on every query. The tests cover Studio, collaborators and the routes fixed in phase 1, but a new query that forgets the workspace would not be caught by the database.
- Meta grant revocation and the assistant-import orphan sweep (section 6).
- Supabase's storage HTTP API itself and pg_cron jobs weren't part of the database tests (only the tables behind them).
