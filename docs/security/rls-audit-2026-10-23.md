# SOCIA database security audit: RLS, functions, storage, service role (2026-10-23)

Branch `rls-audit`, from `main` after the two security-hardening PRs (#74, #75). Migration: `supabase/rls-audit.sql`.

Status labels:

- **FIXED AND TESTED:** fixed, and a test against a real Postgres database (or, for app code, an automated test) fails if the fix is undone.
- **FIXED BUT NOT DATABASE-TESTED:** fixed in server code and unit-tested, but not proven through the database.
- **VERIFIED SECURE:** checked and found correct; tests now pin it.
- **REQUIRES MANUAL ACTION:** needs Noah.
- **NOT FIXED:** left, with the reason.

The database is not "verified secure" in general. What is verified is listed, and the tests that verify it are in `supabase/tests/`.

## How it was tested

Every check below runs against real Postgres, not mocks. `supabase/tests/harness.ts` builds a PGlite database (Postgres 18) with Supabase's roles (`anon`, `authenticated`, `service_role`), its default grants, `auth.uid()` from the request JWT, and storage with RLS. It then applies **every SOCIA migration in production order**. Each test request runs the way PostgREST runs one: a transaction with `set local role` and the JWT claims.

The people in the tests are:

- signed-out (the anon key)
- customers A and B
- an agency owner O with two Brand Workspaces (W1, and the confidential W2)
- an Admin and a Member of W1
- a member who gets removed
- a brand-new user

|---|---|---|

**Policies that admit every signed-in person** (`USING (true)`), both VERIFIED SECURE and recorded in `rlsModel.test.ts`:

- `plan_config_overrides SELECT`: plan limits and prices, the same numbers the pricing page shows.
- `publisher_heartbeat SELECT`: when the publisher last ran; no customer data.

Every other policy names the caller (`auth.uid()`, or a workspace-role helper that reads it).

**Protected columns** (VERIFIED SECURE, tested):

- `profiles`: plan, plan overrides, Stripe ids, subscription status, trial and period (trigger).
- `workspaces`: `plan_suspended_at` (trigger), and `owner_id` can't be handed over (policy).
- Connection tables: identity and workspace (trigger; and no browser grant at all).
- `tracked_competitors.is_active` (trigger).
- `workspace_members`: only `role` is updatable, by the owner.
- `workspace_invites`: only `revoked_at` is updatable.
- `alert_events`: only `read_at` and `dismissed_at` are updatable.

Owner-writable tables (posts, plans, Studio, snapshots) can be edited by their owner directly. That is safe because nothing trusts those rows for authorization. The publishers re-check the plan's scheduling entitlement and each account's pause flag on every row, and token reads always filter by the row's own owner.

## 3. Policies added or modified

All of these are FIXED AND TESTED.

- **Invites (security-hardening.sql §12, mirrored in team.sql).** The single "owner or Admin may do anything" invite policy was split into three:
  - read: the owner, or an Admin for Member invites
  - create: the same, with `created_by` = the caller
  - cancel: the same, and only `revoked_at` may change
- **`discovered_accounts`:** now has the workspace guard trigger (rls-audit.sql §2).
- **anon grants:** Supabase's default table and sequence grants to `anon` are revoked on every `public` table, including tables created later by the SQL editor (rls-audit.sql §3).

## 4. Dangerous policies and migrations removed or neutralised

## 6. Storage buckets audited

| Bucket | Public | Status |
|---|---|---|
| `studio-sources` (raw clips, frames, audio) | no | VERIFIED SECURE: owner-folder policies for every command. Other customers, anon, and an Admin's or Member's own session can't list, read, overwrite, upload into or delete it (tested). |
| `scheduled-media` (post media, Studio exports) | **yes** | Listing, upload, update and delete are owner-folder only (tested), with MIME and size limits. **Anyone holding a file's exact URL can read it.** See below. |

**Public media (NOT FIXED, design decision).** Instagram and Facebook fetch post media by URL, so the bucket is public. File paths are `<user uuid>/<post uuid>/<n>_<name>`, two random UUIDs (unguessable), and nobody can list them (fixed in phase 1). The exposure is therefore "whoever has the link": SOCIA's own pages, the platforms, and anyone a link is shared with. The minimum-exposure design would be:

1. Make `scheduled-media` private.
2. Hand Instagram and Facebook a short-lived signed URL (about an hour) at publish time.
3. Show previews in SOCIA through signed URLs too.

That touches every place media is shown or published (composer, calendar, MCP `list_media`, the Instagram, Facebook and YouTube adapters), so it is a separate change, and it needs a live publishing test. Recommended next.

## 7. Service-role operations audited

All 34 files that create the service client, plus every one of the roughly 410 `ctx.client` queries (the service role for invited people), were read individually. No critical issues; one high, now fixed.

**Verified secure:**

- Every cron or job is behind `isCronRequest`.
- Every webhook or callback checks its signature or OAuth state: Stripe `constructEvent`, Meta `signed_request` with freshness, `verifyOAuthState`, and the YouTube/TikTok state cookie with PKCE.
- Every RPC `p_user` comes from the server.
- No service key or platform token reaches a response.

## 8. Cross-workspace findings, summary

Through the database (a browser session): none. Customers are isolated on every table, and an Admin's or Member's own session sees none of the owner's data (tested). Through server code (the service role): S1 to S12 above, all fixed.

**Removed members** (tested in the database): access ends on the very next request. The workspace list is re-read through their own session each time, and they can't re-add themselves.

**Changing a workspace id in a request** (tested): a session can't write a row into a workspace it doesn't own, and pointing `active_workspace_id` at someone else's brand reaches nothing.

## 9. OAuth token exposure

VERIFIED SECURE, tested.

- The Instagram, Facebook, YouTube and TikTok token tables, plus pending Facebook Page tokens, have no browser grant at all, not even for the row's owner.
- The assistant (MCP) tokens, codes and connections are server-only too, and its tokens are stored as hashes.
- The server reaches the token tables through the service role, with an owner filter on every query (`privateTables.test.ts`).
- YouTube uploads no longer hand the browser a token (phase 2).
- Production was probed after phase 2's SQL: `permission denied` on the token tables.

## 12. Remaining risks

- **Public media URLs** (section 6): readable by anyone holding the exact link.
- **Guests' isolation lives in server code.** The database can't separate an owner's brands for invited people, because their requests use the service role. The workspace scan test and the per-feature tests cover today's code. A new query written outside `ctx.client` (a lib function handed the client) is not scanned; the agents read those by hand this time.
- **Pre-workspace posts** (workspace NULL) are reachable from any of the owner's brands by id, by design for old data. Brands deleted from now on cancel their queue first, but their old drafts keep a NULL workspace.
- **Owners can edit their own analytics snapshots** (`account_snapshots`, `platform_snapshots`). That only affects their own numbers; restricting it to the server is possible later.
- `PATCH /api/plans` lets a Member edit a saved plan (it is treated as a draft).

## 14. Safe production deployment

1. Merge this PR and let Vercel deploy. The code changes work with or without the new SQL.
2. Then run `supabase/rls-audit.sql`. What it changes:
   - **search_path:** it only sets `search_path` on functions.
   - **`discovered_accounts`:** it adds one trigger (it only refuses foreign workspaces).
   - **anon grants:** it revokes signed-out (anon) table grants. If any signed-out page had read a table it would now get "permission denied" instead of an empty result. Every signed-out path was checked: public pages query only after sign-in, the API routes refuse first, and browser code never queries tables.
3. **Check after running:**
   - Signed out: the landing page, `/pricing`, `/login`, `/signup`, `/privacy` and an invite link load.
   - Signed in: Dashboard, Calendar, Create post, Studio and Settings load.
   - As an Admin: inviting a Member works, inviting an Admin is refused.
   - In the sidebar's activity panel, switching brand shows only that brand's posts.
4. **Rollback, if a signed-out page breaks:** `grant select on public.<table> to anon;` for that table restores the old behaviour while it's fixed (RLS still denies its rows).
